The .gim file

Every REDGIM analysis lives in a .gim file. It holds everything needed to reopen the analysis: the images, the regions of interest, the reference values and the settings - and, once processed, the result as well.

That is why you can send a .gim to someone else and have them open exactly the same analysis, with no separate photos and no settings to write down.

It is not a closed format​

A .gim is, on the inside, an ordinary ZIP file. No encryption, no proprietary format, nothing hidden.

That is deliberate. A scientific data file that only its own program can read is a problem: when the program goes away, the data goes with it. Here, any computer with an unzip tool can open it.

To inspect it, rename the extension to .zip and open it normally - or point the unzip tool straight at the .gim, which most accept.

What is inside​

analysis.gim
 ├── data.json          how the analysis was set up
 ├── photo.jpg          the images, at original size
 ├── photo_thumb.jpg    thumbnail of the first image
 └── result/            only exists after processing
      ├── report.html   self-contained report
      ├── charts.json   the charts as data
      ├── *.svg         the charts as images
      └── *.csv         metadata, histograms and peaks per ROI

data.json​

The heart of the file, and it is JSON: a text format that stores data as pairs of key and value. It opens in any editor, the notepad included, and reads without any special program.

In readable text, it describes:

  • identification - analysis name, operator, creation and edit dates;
  • approach and method - prediction or comparative, and which algorithm;
  • properties - what is being measured, with unit and precision;
  • roiConfig - the size of the regions of interest, in pixels, and the shape;
  • images - name, dimensions and, for each one, the list of regions of interest.

Each region of interest carries the centre position normalised from 0 to 1, the type (blank, standard, sample, or the group letter in Comparative Mode), an optional code and the reference values.

Normalising the position is what lets the same marking hold regardless of resolution: multiplying by width and height gives the pixel.

See the schema of the stored data

          "type": "BLANK",

Three things worth noticing:

The histogram is stored. Each region carries the 256 counts of every channel, which is why a .gim reopens its result without reading the images again.

The position is normalised. x and y run from 0 to 1 and point at the centre of the region. Multiplying by width and height gives the pixel - that is what makes the same marking valid at any resolution.

props holds the reference values, one per property declared in properties, in the same order. On a blank or an unknown sample they stay at zero.

The images​

They are kept as they are: full resolution, no recompression, no cropping. A 4160×3120 phone photo keeps its 3 MB inside the .gim - which is why the file tends to be large, and it is the price of being able to redo the analysis from the original pixels.

You can get them out without unzipping anything: the app explorer exports the images of an analysis.

result/​

It only appears after the analysis has been processed and the final file generated. The report.html opens in any browser without needing anything beside it, and charts.json carries the same charts as numbers, which is what allows redrawing them interactively.

A .gim without the result/ folder is an analysis that was set up but not yet processed.

Opening it without installing anything​

→ Three analyses ready to open

This site's Results Viewer opens a .gim straight in the browser and shows the images with the regions of interest drawn on them, the ROI table and, when present, the result report. Nothing is sent to any server - the file is read on your machine.

Care​

Opening and looking is safe. Unzip as much as you like: nothing you do to a copy touches the original.

Re-zipping works too. Unzip it, change things, zip it again as an ordinary ZIP, rename the extension back to .gim, and the app opens it. The format carries no signature and no index of its own to preserve.

Renaming the file is safe. The outer name does not matter: what counts is the content, and the names declared inside it.

Changing the content is another matter

The data.json and the images are consistent with each other: the file names declared in the JSON must exist in the package, and the region positions depend on the declared dimensions. Touching one without the other leads the app into unpredictable behaviour - from refusing to open to opening with the regions in the wrong place, which is worse because it does not look like an error.

If you are going to edit it, keep a copy first.
